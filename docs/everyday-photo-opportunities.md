# Everyday photo sharing without a special event

The reported timeline showed a selected opportunity triggered by Maya and Becca planning a future weekend, then `no message produced`. That did not establish an event veto or character refusal. Code inspection found that background photo context preferred storyline summaries over actual activity; the selected opportunity was rolled again in the turn pipeline with different text; completed/replayed actions and empty replies could both surface as an unexplained zero-message result. Generic busy status also vetoed photos even when the concrete activity was compatible with a quick snapshot.

## Behavior

- Current physical activity supplies photo context. A calendar event, storyline, visual punchline or milestone is not required. The explicit `; ongoing situation:` suffix is excluded from physical photo context; the full story remains available as conversational knowledge and memory.
- A character may decide to share an everyday selfie, coffee, pet, object or view while doing ordinary things. Generic busy status is not an automatic photo veto. Sleep, driving, surgery/emergency/patient care, phone-away instructions and private-context restrictions still block incompatible photography. Busy characters still control whether to share, and generic text initiation remains subject to its existing availability rules.
- A worker-selected opportunity is passed into the same normal character turn. Eligibility, canonical scene, boundaries, consent and image budgets are rechecked, but the opportunity is not randomly selected a second time. Explicit developer controls remain separate. Ordinary user-conversation photos do not require a world-worker event.
- The bounded hourly chance sample uses conversation/character/time, not the wording of a rotating storyline. Character-specific probabilities and frequency preferences remain unchanged. Opportunity/action identity still includes the actual context to distinguish grounded moments; repeated polls do not reroll the same sample.
- Terminal photo actions are recognized before reserving another autonomous text budget. Failed/uncertain actions are not regenerated. Running/prepared actions retain the existing safe recovery workflow.
- Real attachment delivery reports `photoSent` and known image-request status from the saved outbox. The timeline labels a delivered photo versus text without a photo. Empty model output on a selected photo opportunity records an explicit silent choice. Replayed/failed actions have explicit technical reasons rather than being mislabeled as character refusals. Legacy records remain unchanged and unknown generation status is not invented.

No provider/model, canonical identity/reference, image screen/retry, media storage, push, daily/monthly image limit, memory/relationship formula or database migration changes are introduced. Supporting broader everyday opportunities may increase use within the existing image/worker limits; no unlimited or forced photo generation is added. The user can continue sending photos and requesting images normally.

Existing scene, memory, relationship, provider failure and notification tests remain applicable. Automated tests do not prove live model willingness or visual quality.

After review/merge, sync and build/publish code normally. No new SQL or secret is needed. In Photos, preview a simple current-activity selfie and use the existing delivery/status/recovery controls. In the World timeline, check the actual physical trigger and whether the character sent a photo, sent text only, chose silence or encountered a specific technical block. An ordinary busy day can allow a photo; an unsafe activity cannot. Old timeline entries retain their historical wording. Do not clear histories or repeatedly regenerate an uncertain action to test this.
