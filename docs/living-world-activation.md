# Living world: review, activation and testing

## What executes offline

An authenticated POST to `/api/public/jobs/world-tick` acquires the existing database lease, recovers prepared deliveries, sweeps visible notifications, advances social events/storylines and checkpoints each selected character's activity. It then evaluates due promises, personality-specific initiation and optional spontaneous photos through the same `runTurn` used for conversation replies. No browser is needed. A tick catches up to the present; it does not invent a backlog of messages or award relationship points for elapsed time.

The worker processes 20 conversations per run, with a durable ID cursor for fairness, at most four paid text calls per run and 12 autonomous calls per user per UTC day by default. Exhausting the AI budget does not stop structured world progression. Practice conversations get world checkpoints but no real-clock automatic messages. The hidden schedule preview is deterministic and read-only; existing controlled photo tests work in either mode. We did not add Hybrid mode or change relationship scoring.

World checkpoints and event histories are durable. `world_records` holds explicit, source-quoted future intentions and stable NPC/object/preference/commitment claims. User-evidenced facts can be confirmed; character improvisations remain tentative; jokes are excluded. Code canon remains authoritative. Pending intentions expire 48 hours after their due time, defer with bounded backoff if unfulfilled, and require actual attachments to fulfill photo promises. A failed/uncertain image attempt cancels that automatic attempt rather than charging it again. This extraction applies to new replies; old conversations and memories are not rewritten or retroactively converted.

## Activation after review — no SSH required

1. Merge the review branch into GitHub `main` only when ready for Lovable to synchronize it. This implementation has not changed the published app.
2. In Lovable chat, request: **“Synchronize GitHub main. Review and apply only `drizzle/migrations/0010_persistent_world.sql` against the existing database using your backend tools. Preserve all data. Migrations 0008/0009 already installed the photo-delivery RPC; 0010 extends it. Confirm `world_runtime_status()` returns version 1 and `deliver_photo_turn(NULL)` reports worldVersion 1. Do not reset tables, rerun old migrations, or publish yet.”** The migration is additive; the existing delivery implementation is retained as a private base function within its transaction. Local PostgreSQL tests install it from a fresh schema. Back up production using the platform's normal facilities before applying any migration.
3. In Lovable Cloud server secrets, retain `OPENAI_API_KEY`, `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` (use existing platform server bindings), `VAPID_PRIVATE_KEY` for push, and set a strong random `LOVABLE_CRON_SECRET`. Do not put these in frontend variables. Text remains direct OpenAI `gpt-6-luna`; image provider/reference files and photo content rules are unchanged.
4. Optional server limits: `AUTONOMOUS_AI_DAILY_LIMIT=12` (0–100), `IMAGE_DAILY_LIMIT=2` (0–50), `IMAGE_MONTHLY_LIMIT=20` (0–1000). Zero stops the corresponding paid action. Image limits apply per conversation with an additional shared per-user cap of three times each limit. Defaults therefore allow at most six attempts per user/day and 60/month across characters. Attempts include failures and user-requested images; UTC boundaries. Curated existing photos incur no image-generation cost. Character-specific spacing, boundaries, recent-message cooldowns and quiet hours still apply.
5. Preview/test first, then use Lovable **Publish / Update** when satisfied. Obtain the published HTTPS app URL. Never use a temporary preview URL for a persistent scheduler.
6. In **GitHub repository → Settings → Secrets and variables → Actions**, add secret `LOVABLE_CRON_SECRET` with the same value as Lovable. Add variable `WORLD_TICK_URL=https://YOUR-PUBLISHED-HOST/api/public/jobs/world-tick`. Leave variable `LIVING_WORLD_ENABLED` unset until ready. The checked-in workflow does nothing without it.
7. After the backend migration and published build are validated, set repository variable `LIVING_WORLD_ENABLED=true`. In **Actions → Living world tick → Run workflow**, trigger once and inspect the summary and the app's developer **Living world timeline**. Scheduled runs then request a tick every five minutes, independently of the app. GitHub scheduling can be delayed or disabled on inactive repositories; it is not a precise real-time clock. An existing managed scheduler may call the same POST instead. Use one configured scheduler and monitor its heartbeat. The database lease also prevents overlapping workers.
8. Close the app, allow multiple scheduled runs, then reopen **Simulation debug → Persistent world diagnostics**. Check changing checkpoint timestamps/activity, recent completed events, `workerHealth.lastTick`, photo decisions, pending intentions, delivery events and image attempts. A successful workflow alone does not prove a paid image or a phone push succeeded.

Disable automation by unsetting `LIVING_WORLD_ENABLED`; disable paid autonomous calls with server `AUTONOMOUS_AI_DAILY_LIMIT=0`. `CHARACTER_AI_DISABLED=true` remains the existing global text kill switch. Configure project billing alerts/limits in OpenAI too; attempt limits are not a guaranteed dollar cap.

## Safe tests and controlled demonstration

Run `npm test`, `npx tsc --noEmit`, `npm run build`. No production service-role key or paid provider is required. The offline demonstration is:

```sh
npx vitest run src/test/world-offline.integration.test.ts
```

It runs real world-tick, character decision, canonical-reference image prompt, private-storage upload, budget reservation and PostgreSQL delivery code against a disposable database. Only paid text/image provider outputs and storage are fake; it starts with no user messages and checks one delivered contextual clinic selfie, independent events, attachment linkage, preserved memory, replay safety, budget-zero behavior, Practice isolation and terminal image-provider failure. Separate PostgreSQL tests cover rollback, ownership, pending-photo fulfillment, spending quotas, delayed delivery and notification claims. This demonstrates plumbing, not live model quality or real push delivery.

For a real controlled test without SSH: retain `ENABLE_DEV_PHOTO_ACTIONS=true` and the exact allowed account IDs in `DEVELOPER_PHOTO_USER_IDS`. Open the character's hidden debug screen, preview a grounded current visual moment, then **Ask character to share**. This uses the normal policy/generation/delivery pipeline and can incur charges. For Tess, use a genuine clinic break; emergency or patient work remains ineligible. Only mention coffee, the fidget button or foster puppy if those facts exist in this conversation's memories; nothing in the engine forces those events or a dinner date. Use **Living world timeline → Run tick now** to evaluate the unforced autonomous world pipeline without sending a user message. Characters may decline, and a tick may legitimately send nothing. Do not repeatedly retry an ambiguous image action.

## Costs and limitations

No paid generation or production verification was performed in this change. Real Maya delivery was reported by the user in earlier testing. Tess's clinic scenario passes with fake paid providers and actual canonical-reference routing; live Tess generation still needs the controlled check above. Pet/environment photos retain the existing pathway and optional Mabel reference; no new identity images are supplied.

Budget by **successful and failed image attempts × current provider image price (including reference input tokens)**, plus Luna input/output tokens and storage/push hosting. Defaults cap autonomous text attempts at roughly 360 per user in a 30-day month and image attempts at 60 per user per calendar month; manual chat, debriefs and vision have their existing separate protections. Exact dollar cost depends on current OpenAI rates and actual token usage; no unverified price is embedded in code. Image requests and user-photo vision descriptions can still use Lovable credits if only their existing `LOVABLE_API_KEY` fallback is configured; character text has no gateway fallback.

World events remain bounded, structured fictional simulation using existing schedules and storyline templates. This does not create an unlimited AI story planner. Read-only Practice preview is not a durable alternate-time universe. Promises without explicit quoted wording or an actionable time may not be extracted. Tentative NPC/object records guide continuity but are not automatically promoted into permanent canonical NPCs. Existing unstructured memories are preserved. Delivery uses the existing at-most-once push claim: a provider/network failure after claiming may lose a notification rather than duplicate it. Prepared paid deliveries and uncertain provider failures retain existing recovery limitations; inspect a stuck action before manual intervention. Quiet hours currently use the application's America/New_York convention. Production schema, platform request-duration limits, provider permissions and scheduler operation require deployment validation.
