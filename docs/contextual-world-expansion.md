# Contextual photos, identity and encounter expansion

Baseline: GitHub main **ddd5e67**, including Lovable's recent migration/type updates through 0014 and the merged world/video work. Branch: **codex/contextual-photos-and-encounters**. No production SQL, deployment, paid image/text generation, secret change or source-portrait replacement was performed.

## Photo pacing

Ordinary reply photos were previously blocked by 7/12/20 intervening character messages and a one-hour minimum; autonomous selection additionally applied personality time/message gates. These stacked restrictions could prevent sensible requested/contextual photos even when consent, provider and budget were available.

`photo-pacing.ts` now separates a direct visual request, a visually relevant exchange and ordinary chatter. At normal frequency Tess can consider a direct photo request after three minutes without filler messages; a visual exchange normally uses ten minutes plus one intervening character message, ordinary chatter thirty minutes plus two. Maya is faster; Claire/Ben slower; Jordan most selective. Rare/frequent preferences scale the intervals. These are opportunity floors, not promises to send an image. The character can decline. Romance scores/flirting do not grant permission.

Message nudge thresholds are now rare/normal/frequent **6/3/1** rather than 20/12/7. Autonomous opportunities retain distinct personality windows and stable opportunity keys; relevant visual context can shorten the autonomous time floor to 60% of its previous value and modestly increase selection probability. Polling cannot reroll the same opportunity. Foreground direct/contextual requests use the shorter reply pacing; the worker does not send everyone a scheduled photo.

Unchanged protections: schedule/sleep/driving/clinic privacy checks, photo boundaries and relationship eligibility, separate willingness, composition repetition checks, group-photo rejection, canonical reference bytes, visual/text screens, private storage, action deduplication, atomic delivery and no automatic uncertain-image retry. Existing daily/monthly limits remain. New **rolling 24-hour** checks are enforced under the same database budget lock to prevent a burst around midnight. Defaults remain two attempts/conversation/day and 20/month, with a shared user ceiling of six/day and 60/month; the rolling caps also use two/six. Failed attempts count. Curated images remain distinct from billable generation.

The existing developer photo preview includes pacing details and budget status. Character debug uses current pacing and an independent last-attachment query, rather than inferring time eligibility from the last few messages alone. Stronger opportunity selection is not a claim that a live model will always choose a photo.

## Focused photo viewer

Received curated/generated photos, user photo bubbles and shared-photo gallery images can open a focused full-screen viewer. It has close/Escape/focus restoration, safe-area spacing and original-resolution images. **Save / share photo** uses native file sharing where supported (the OS may offer Save Image/Files), otherwise a Blob download; platform/browser behavior still varies. It shares image bytes rather than the private signed URL. PNG/JPEG/WebP/GIF/AVIF extensions are preserved where known. Failure is visible and never starts a generation. Existing photo metadata/storage/history is retained. Video playback/upload remains unchanged.

## Canonical identity versus current profile photo

The original five asset-backed portraits remain immutable generation authorities. `canonical-profile.server.ts` still supplies their exact JPEG bytes, never the active avatar or a previous generated image. No existing source image is changed.

New `visual_identity_registry` records owner/entity, approved canonical asset/hash, optional active display-message ID, explanation and update time. Approved hashes cannot be reused for a second character in the same tenant. Missing approval requires null source fields and disables an active portrait. NPC entries begin missing/unapproved; **all six discoverable NPCs still have photos disabled**. There is no UI/API that silently invents an approved face or gives an NPC Tess's default identity.

On an established character's profile, **Current profile photo & identity** exposes the original reference and up to eight delivered casual portrait candidates. Selection requires explicit visual approval and a reason. Candidate requirements include correct owned character/conversation, visible delivery, casual-selfie/candid type, canonical asset/hash match, successful reference-conditioned screen and a private generation receipt. Objects, intimate photos, user uploads, another character's images, unverified older photos and forged metadata without that receipt are rejected. A display update/reset writes a deliberate profile event, not a fabricated incoming message. Replaying the same selection is idempotent. Deleting the source message resets the active reference; it does not replace the permanent canonical asset.

Inbox, chat, People and profile display use the chosen signed image with the original asset as the default. The speaking character can receive only their own update reason in context, so they can explain the change. This does not expose another character's photo or private activity. **Automatic AI-selected profile changes are not enabled**; this release establishes a reviewed, deliberate change path. Model screening is probabilistic and explicit user visual acceptance remains necessary. New NPC source-image submission/approval and generation adapters are follow-up work; a registry row alone does not enable selfies.

## Places and discovery

Four existing places are retained. Three additional virtual destinations bring the public registry to seven:

- **H.O.P.E. Drop-In · virtual scene**, Altoona grounding. The scene, all people, activities, illustrative pin and simulated hours are fictional. This is not a representation of real visitors, staff, services or actual operating hours.
- **Canal Green**, a fictional park near Hollidaysburg.
- **The Open Porch**, a fictional bakery/casual hangout near Altoona.

The existing map, search, place views, opening hours and virtual travel rules consume the expanded catalog after migration readiness. No GPS API is used. Existing labels/profiles are not overwritten by seeding. An active public plan links to its place; visiting can expose the same schedule-eligible NPCs there, without asserting event attendance or inventing a group interaction.

Three new explicitly fictional adults bring discovery to six: **Mira Dalton**, 32, a ceramicist/walker at Canal Green; **Theo Finch**, 35, a baker/puzzle enthusiast at The Open Porch; **Inez Carter**, 41, an invented craft volunteer in the fictional drop-in scene. Their routines/interests/personalities differ. They are not based on real private people, do not replace existing supporting NPCs, and have no automatically approved portraits. Existing Rowan/Leah/Nolan profiles and the original supporting circles remain intact.

Co-location never creates friendship or messaging access. A completed explicit conversation establishes an encounter; a failed first generation no longer leaves a phantom “met” connection. Contact exchange still requires some conversation, model willingness and the user's explicit acceptance. No scores, attraction or relationship stages are artificially advanced.

An established contact's **actual delivered** message can offer an introduction, such as “You should meet Mira Dalton.” Only supported explicit positive phrases naming a registered person surface a **Meet…** chip. The owner-authorized service verifies the message, stores the introduction and opens the public place. It does not teleport the user, create friendship or exchange numbers. People distinguishes an introduction from someone actually met/contacted. Only the source character's name and the forwarded introduction scope may reach the new NPC, never the private original transcript. No new friendship/canon facts are seeded to force these messages; introductions need legitimate conversational/world context. NPC invitations and generalized character-to-NPC meetings are not yet implemented.

## NPC memory and optional follow-through

Supporting dialogue still uses the existing direct **gpt-6-luna** structured-output service. Memory/intent extraction rides in that same response; no separate reflection/model loop or embedding provider is added. Up to three short user-reported memories per reply require exact quotes from the current user message. They are retained with evidence, never promoted into the canonical personality/biography. Retrieval includes at most twenty of this owner/NPC's memories plus the existing bounded transcript. No other character/user's conversation is queried.

An NPC can record an optional pending follow-up only when its actual reply makes an explicit promise with an exact quote and a due time 30 minutes–7 days ahead. Unsupported quotes, vague claims or invalid times are ignored. Pending identical promises are deduplicated. The memory, promise, reply and contact willingness commit in the existing town transaction. Old transcripts are not retroactively mined or rewritten.

Background follow-ups require **both** server `ENABLE_NPC_FOLLOWUPS=true` and that exchanged contact's **Allow occasional follow-ups** checkbox. The flag defaults off. They additionally require an actual due/unexpired promise, the NPC's routine availability, at least one Real-Time primary conversation, user quiet-hours compliance, a thirty-minute gap after recent thread activity, no in-flight NPC reply, no provider pause, an available global worker budget and the existing shared per-user autonomous quota. Limit: one successful follow-up/NPC/24 hours, at most one attempted NPC action/user/selected tick. The existing forty-turn NPC daily ceiling also counts these actions. A model can choose an empty reply and silence; no synthetic user bubble or fake success is inserted. Provider failures/uncertain reserved actions become terminal rather than automatically re-inferred. Follow-up turns cannot create more follow-up intentions, preventing an AI-to-AI/self-perpetuating loop.

The normal authenticated `/api/public/jobs/world-tick` advances this queue when explicitly configured. No new scheduler is installed or activated. Existing primary messaging/photo/push paths remain. New NPC follow-ups appear in their existing inbox threads and durable action/intention records; **NPC-specific OS push is not implemented in this slice**. Existing developer town-action diagnostics show autonomous/completed/failed receipts. All-Practice worlds skip paid NPC initiation; this is not an accelerated persistent Practice town.

## Migration and security

It adds `town_memories`, `town_intentions`, `visual_identity_registry`, `town_introductions`, opt-in/last-follow-up fields, an autonomous action mode and supporting service-only functions. Existing `town_command` is replaced in the new migration to share its transactional, locked receipt/delivery path, accept registered NPCs instead of a hardcoded three-name list, and atomically save evidence-backed continuity. Existing action statuses/IDs remain valid.

The image budget function preserves UTC daily/monthly checks and adds rolling checks under its existing user lock. New tables use owner-scoped SELECT/RLS and service-only writes; the portrait/intro mutation functions are service-only. Primary text reads of profile context use owner-authorized table reads, not a privileged capability RPC. Source/active avatars and NPC memory are distinct from canonical bytes. Existing messages, relationships, scores, photo/video objects, established plans and source assets are not reset, migrated into new identities or deleted. The test adapter installs migration 0015 into disposable PostgreSQL; no production credentials are required.

Without 0015, existing messaging/media work and display avatars fall back to originals; expanded discovery and profile changes are gated by capability checks. The new follow-up flag alone cannot bypass a missing migration, contact consent or per-contact opt-in. Provider/model settings are unchanged.
