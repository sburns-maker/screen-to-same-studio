## Tess app
- Voice creation, Studio selectors, scripted auditions and live-call voice assignment use the shared voice-design cast allowlist, so new contacts cannot silently disappear from sibling voice paths; presets are exhaustive over that cast.
- Successful direct text-AI calls reconcile conservative in-flight reservations to reported token usage in the same window; failed or unknown usage remains reserved. Living Experience failure logs use allowlisted reasons and phase/operation IDs, never transcript or raw provider errors, so diagnosis does not expose private context.
- Voice Studio auditions reserve a durable lease via `reserve_voice_audition` (one active per developer, daily/30-day caps) before any paid request, and a server sideband supervisor (`voice-studio-audition.server.ts`, kept alive by `keepAlive` waitUntil) closes the session at the deadline; browser timers alone must never authorize paid sessions, and failures are never auto-retried.
- Scripted and Tess conversational audition modes share validation and prompt builders in `voice-audition-modes.ts`; editable performance/cue drafts use separate device-local storage and are snapshotted for each explicitly confirmed audition so server and client prompts stay aligned without changing saved voices, character state or the audition lease.
- Tess model prompts live in `src/lib/tess.server.ts`, with direct OpenAI configuration in `src/lib/text-ai.server.ts`. They are reached only via server fns in `src/lib/tess.functions.ts`, keeping prompts, hidden-state logic and keys off the client.
- State math (delta clamping, difficulty scaling, stage derivation) lives in pure `src/lib/tess-logic.ts` with tests in `src/test/tess-logic.test.ts`; stages must emerge from state, never points.
- Delayed replies are stored with a future `visible_at`; the client hides messages until then. Unrevealed text replies are replaced when the user sends more; already-generated pending photo attachments are retained so their images are not charged again.
- Tess's photos are hybrid: curated library first (`src/lib/tess-photos.ts` rules, `tess-photo-images.ts` images), then optional generation via the provider abstraction in `src/lib/tess-image.server.ts`, always conditioned on the private canonical reference (`tess-reference/canonical.jpg`). Eligibility/cooldown is pure and tested; the server validates every model choice. Generated images live in private `tess-photos/<userId>/` with a `generated_images` row and are never regenerated; failed image actions send no misleading caption and are never automatically regenerated.
- Photo policy separates technical capability, pure eligibility, and structured model willingness in `photo-policy.ts`; runTurn enforces all three, persistent conversation refusal scopes, and independent romantic intent so scores or opt-in never grant consent. Mature portraits use a separate category and conversation preference, never the ordinary-image prompt.
- The social world is deterministic and AI-free: `src/lib/social-logic.ts` (pure, seeded by stable event ids — re-planning a week must always produce identical output) plans NPC circles, links, shared events and knowledge; `src/lib/social.server.ts` persists via upserts inside the world tick. Knowledge isolation is enforced by querying only the character's own `character_knowledge` rows in runTurn — never widen that query.
- Multi-week situations use `storyline-logic.ts` for bounded deterministic branching and `storyline.server.ts` for shared-event root checkpoints, immutable milestone events, participant-only current knowledge and idempotent personal outcome memories; advance only inside the managed world tick, independently of its AI budget, to keep closed-app continuity cheap and recoverable.
- Web Push uses a dedicated push-only worker served by `src/routes/api/public/push-worker.ts` (scope `/api/public/push/`), separate from the offline `/sw.js`; static files are blocked by the private-publish sign-in wall, `/api/public/*` is not.
- Tess voice is enforced deterministically by `src/lib/tess-voice.ts` on her output and on her past lines in the transcript; prompts alone drift because the model imitates its own history.

- Spontaneous photos use the pure `photo-opportunities.ts` rules and the existing turn pipeline. `photo-delivery.server.ts` reserves stable actions in the service-only job ledger; migration `0008_atomic_photo_delivery.sql` commits delivered messages, attachment metadata, state and memories atomically. Never automatically retry an uncertain image request. Developer photo actions require both an explicit flag and a user-ID allowlist.

- Media/profile expansion: `currentCanonical` in `profile-media.server.ts` resolves the owner/character's explicitly approved private reference, otherwise the original bundled portrait. All production character-image paths must pass that resolved reference to `generateTessImage`; never derive identity from the active avatar or promote generated output automatically. Avatar-only changes preserve the anchor. Canonical changes require explicit visual approval, immutable private bytes, integrity hash and an audit record (migration 0017). Do not expose signed storage URLs through sharing/copy actions. User-uploaded video remains separate from optional, unimplemented paid AI video generation.

- Character photography profiles/scenarios live in pure `photo-personality.ts`. Use actual current context, not preferred setting examples, as evidence. Only visible screened same-conversation photo metadata supplies short-lived visual continuity. The 20-minute hint lifetime is not a sharing cooldown. Pass the plan through the shared image service; keep caption guidance in the dialogue call. Never use generated pixels as canonical references, change model/retry/budget rules for a style preference, or widen character knowledge retrieval.
- Live character calls (`live-calls.ts` pure rules, `live-calls.server.ts`, `live-calls.functions.ts`, route `/live-call/$conversationId`) reserve a durable `live_character_calls` lease (one active per user, daily/30-day caps) before any paid GPT-Live session; the server closes overdue sessions via heartbeat and the world-tick sweep, and phone voices come from the Studio-set `character_voices` table (env `GPT_LIVE_VOICE_*` is fallback), so browser timers never authorize paid time. Schema for these tables lives outside the read-only drizzle folder (applied directly, mirrored in docs/live-character-calls.md).
- Approved bundled canonical portraits retain their original JPEG or PNG bytes in source control rather than CDN-only pointers, so server-side identity references remain immutable and available without runtime fetching.
- Internal world-installation rows remain service-only; the static phone directory is signed-in read-only with RLS, preserving existing service RPC and foreign-key access without allowing client mutations.
- Travel storage uses owner-scoped RLS and explicit authenticated/service grants with plain user UUIDs; journal access also checks parent-trip ownership to prevent cross-owner writes.
- Living Experience cast additions must update seed, plan protection and both legacy calendar/venue batch guards together; otherwise a supported character can lose outing access or completion ownership.
- Calendar payloads and prepared-reply recovery resolve exact, unambiguous owner-scoped public venue labels to registered keys; preserve unknown venue validation and never resurrect failed/stale jobs, so label mistakes cannot block already-paid delivery.
